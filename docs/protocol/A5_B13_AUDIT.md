# a5.b13 的离线证据

> 历史原生证据：文中工具/命令对应采样版本，未随精简运行包保留。当前入口见 [协议指南](../PROTOCOL.md)，旧实现可从 [整理记录](../MIGRATION.md) 的固定提交追溯。

> 历史研究资料，来源 `codex/keeta-project@6197c528`；保留当时的观测与未完成项，不代表新项目当前状态。当前规则见 [字段状态](../MTGSIG_FIELDS_STATUS.md)，复跑入口及已修正结论见 [离线研究指南](https://github.com/xiaozeng2296/keeta-server/blob/2ec895ea20c0ca273ee036af5dc0d8fed55d1f97/docs/research/OFFLINE_RESEARCH.md)。文中的旧 `dump/`、抓包及设备路径仅作证据索引，原材料未随仓库发布。

> 2026-10-02 补充：[b 系列原生来源与 render 对照](../research/B_COUNTERS_RENDER_20261002.md) 已定位 b2/b17/b18 计数分支和 b16 上报状态映射。下文计数关系是历史观察，不能替代新原生证据；b13 的历史统计结论仍按本文范围理解。

结论：现有数据不支持把 `b13=33` 解释为风控检测命中，也不支持把它改成 2 来模拟成功登录。
它与采集缓存刷新呈明确的阶梯关系，**疑似采集轮次/刷新计数**；原生写入点尚未恢复，字段正式语义仍待确认。

本轮没有网络、手机或邮箱操作，也没有更改任何画像或签名字段。

## 抓包统计

对项目根目录的 5 份既有抓包离线解出 268 条 a5。另 4 条 mtgsig 缺少 a4、带 d1，属于当前
解码入口不支持的另一字段形态；这些条目未纳入 b13 分布，不宣称其解密失败证明密码不同。

| 抓包 | 可解 a5 数 | b13 分布 | 登录相关证据（零基索引） |
|---|---:|---|---|
| 从app初次打开到登录被拦截 | 65 | 2×54、3×8、5×3 | #801 risk：5，返回 101135 |
| 发送验证码并成功登录 | 26 | 5×5、6×21 | #14 signupapply：5，返回序号；#30 signup：6，返回账户 token |
| 完整版新设备注册登录 | 93 | 2×70、3×23 | #585 risk：2，返回 ticket；#589 apply：2；#601 signup：3，返回账户 token |
| 店铺以及菜品详情和店铺详情 | 11 | 23×8、24×3 | 此段没有登录 risk，不能拿它判断新账户门禁 |
| 新机之后尝试登录 | 73 | 2×73 | #628 risk：2，返回 101135 |

同样的 2 同时出现于成功与失败 risk。成功发码/注册提交的 b13 可以是 2、3、5、6；
因此 `b13==2` 既不是充分成功条件，也不是所有登录阶段的必要条件。

## 与缓存刷新及签名序号的关系

| 来源 | b13 变化 | b8/b9 相对 b7 的变化 | b2 变化 |
|---|---|---|---|
| 完整成功包 | 2→3 | 0→60 秒 | 4..81 → 82..110 |
| 初次打开失败包 | 2→3→5 | 0→60→180 秒 | 12..72 → 73..81 → 83..85 |
| 店铺包 | 23→24 | 2520→2580 秒 | 92..99 → 100..102 |
| 当前手机两个原生快照 | 33→36 | 1861→2041 秒 | 49→50 |

同一次缓存状态下，多次签名的 b2 继续递增，b13 不变。上述每个观测到的 b13 状态组里，
b8/b9 也固定；刷新后出现新状态。两份当前手机原生快照尤其明确：180 秒间隔对应 b13 +3，
但只多了一条被记录的签名。

这支持采集刷新计数假设，而不是请求序号或成功/失败结果标记。不过不能直接写成
`floor((b9-b7)/60)+2`：店铺包的启动相对时长与该公式不符，前后台暂停、刷新触发规则或
其他生命周期事件尚未追清。不能按经过秒数虚构 b13。

当前 b12 大多为 2，但第二份成功登录包有 3 条 b12=1；这也说明不能将先前有限样本的
“b12 恒为 2”推广为所有原生状态。b12 的正式语义同样没有在本轮恢复。

## 33 的来源和当前实现

`dump/incognia_recovery/unlocked_current_01/context.json` 的原生 mtgsig 解出 b13=33，
稍后的 `reporting.json` 解出 36。这两份材料不是协议执行器生成的签名。

`tools/registration_session_probe.py:prepare_sources()` 从 context 的真实 a5 解码完整
`base_collect`，保存到初始 identity。本轮 base-prepared、synthetic-prepared、run01、login01、
login02 沿用这份 base_collect，因此 33 来源清楚，没有被协议脚本新设成检测标志。

`mtgsig/signer.py:FullSigner._fresh_a5()` 更新 b2，并有条件更新 b17/b18；它保留缓存中的
b3、b7/b8/b9、b12/b13。现有实现没有重建原生定时采集生命周期。这是能力边界，不能把
“缓存固定为 33”直接解释为字段已错误，也不能声称长时间协议运行完全复刻了原生采集刷新。

查阅已有 docs、collector 工具、字段索引及当前汇编，没有发现 b13 的可靠 setter/增量点映射。
汇编里同名 collectCount 是 CIPWaterMark 的公开性能采集字段，未证明与 a5.b13 有关，未据此归因。

下一步若需要实现采集生命周期，应先找 b13 输出绑定的原生状态对象和更新入口，确认
初始化、定时刷新、前后台暂停及失败行为，再同时更新对应缓存时间和内容。当前不建议盲改为 2。

## 复现

`tools/audit_a5_b13.py` 只读显式指定文件，输出字段计数、相对时间、阶段结果布尔值和输入 hash；
不输出邮箱、设备标识、密钥、ticket、token 或完整明文。当前派生结果在 `dump/a5_b13_audit.json`。

```bash
python3 tools/audit_a5_b13.py \
  '从app初次打开到登录被拦截.chlsj' \
  '发送验证码并成功登录.chlsj' \
  '完整版新设备注册登录.chlsj' \
  '店铺以及菜品详情和店铺详情.chlsj' \
  '新机之后尝试登录.chlsj' \
  --sample-json dump/incognia_recovery/unlocked_current_01/context.json \
  --sample-json dump/incognia_recovery/unlocked_current_01/reporting.json
```
