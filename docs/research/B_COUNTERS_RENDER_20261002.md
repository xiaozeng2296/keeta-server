## 本次结论

同一账号 #132 的早期首页材料返回 render 403，后期首页材料可以成功。换店、换菜品组后，**只替换 a5 明文中的 b16，并重新计算对应 a5/a2，能够双向翻转 403 / 200**。本次已经定位到字段级差异；尚未拆分验证 b16 内每个数字的独立必要性，也不能推广为所有账号、所有 403 的根因。

b2、b17、b18 的原生读写已定位：b2 是 a5 生成序号；b17 统计经过签名前置流程的 POST；b18 在同一前置流程看到 SDK userID 为 nil 时递增。它们不是账号请求配额或成功次数。本次单项扰动没有复现它们导致的 403。

进一步追踪发现，**b16 三组值是 SDK 三类上报的调用次数和相对时间记录**。旧字段表仅凭三元组形状称其为“加速度/陀螺仪”，没有来源证据，现予纠正。

## b2、b17、b18 的原生来源

原生镜像为 3.12.500 / build 18565 / SDK 5.21.10；Mach-O UUID `3fb544966dc03ccca41b9055fc509adf`；SHA-256 `194747e820db2102408082b0670daa45fc066fb08e0606a341dc63896058130c`。RVA `0x2d0000..0x430000` 与既有真实运行进程代码快照逐字一致。下列地址均为 RVA，不是 ASLR 后绝对地址。#132 的线上材料为 3.12.401；当前原生实现与历史抓包相互支持，但不能声称两个版本的指令布局已逐字对拍。

| 字段 | 当前原生语义 | 写入 / 输出证据 |
|---|---|---|
| b2 | a5 builder 内 32 位无符号原子序号，每进入该生成路径加 1；溢出回零 | 全局 `0x4f0b120`；原子增量 `0x2f6b00..0x2f6b18`；Number 构造 `0x2f3a80`；JSON 插入 `0x2f2bbc` |
| b17 | 签名前置流程将 HTTP 方法转大写，等于 POST 时，32 位原子计数加 1 | uppercase `0x2e3db8`；POST 比较 `0x2e4bdc`；调用增量 `0x2e4f90`；writer `0x2ec5bc`；全局 `0x5015568`；getter `0x2f0a10`；JSON 插入 `0x2f2cc0` |
| b18 | 同一前置流程读取 `SAKEnvironment.environment.user.userID`，返回 nil 时，32 位原子计数加 1 | getter 链 `0x2e4f98..0x2e5028`；nil 分支调用 `0x2e4954`；writer `0x2ec5d8`；全局 `0x501556c`；getter `0x2f0a20`；JSON 插入 `0x2f2cd4` |

b2 的低 32 位以小端四字节进入 a2 收尾，不能拿 b17、b18 或 a10 第二段替代。b17 统计签名前置调用，不保证等于实际发出的 POST 网络请求数；签名后可能取消请求，抓包也可能不完整。b18 的 nil 是 SDK 对象状态，不是 HTTP userid 请求头是否存在；非 nil 的空 NSString 也不会进入增量分支。仅凭 token 不能还原该对象状态。

验证：7 份 Charles 文件解出 566 条当前布局签名；筛选 b2 连续的 428 对，b17 增量与后一个请求是否 POST **428/428 一致**。其中 4 个 GET 例子明确表现为 b2+1、b17不变。登录前抓包的 b18 常随签名前置调用增加；后续菜单抓包保持不变，与 nil 分支解释一致，但抓包请求头不能直接观测 SDK userID。

另以隔离对象执行原生 ARM64 分支：7 种 method / nil / 空对象 / 溢出组合，以及 3 种 b2 增量起点全部通过。Objective-C 返回对象是合成输入，实际条件跳转和原子指令来自上述运行镜像；这不是本轮重新进行真机登录测试。

## b16 的原生结构与生命周期

单例 getter `0x36ce10`、对象指针 `0x4f17988`；构造器 `0x36c224` 将计数/时间置零；a5 builder 在 `0x2f2e4c` 取对象，调用 `0x36d020` 序列化，最终写入 b16。

格式为 `[%d,%ld,%ld],[%d,%ld,%ld],[%d,%ld,%ld],%ld`。每组三元组依次是：**调用计数、最近调用的相对秒数、最近 HTTP 200 回调的相对秒数**。后两项是相对于 SDK 时间基准的时点，不是单次请求耗时；二者差值在对应同次调用时才近似该段间隔。

| 位置 | 对应 SDK 请求 | 原生 request type | 对象偏移：次数 / 调用时间 / HTTP200回调时间 |
|---|---|---|---|
| 第一组 | `/v5/sign` | 2 | `+0x18 / +0x28 / +0x40` |
| 第二组 | `/fingerprint/v1/info/report` | 1 | `+0x1c / +0x30 / +0x48` |
| 第三组 | `/v5/device-info` | 3 | `+0x20 / +0x38 / +0x50` |
| 最后一项 | `resumeTime / 1000 - SDK时间基准`，转整数 | — | `+0x58` |

来源闭环：

- 请求构造函数 `0x31d834` 保存 request type，`0x31ec8c` 使用 type-1 索引分派表 `0x31f2f0`。实际解码的 CFString 分别是上述三个路径，不是靠事件日志名称猜测。
- 调用计数/时间写点：第一组 `0x31d9bc..0x31d9cc`，第二组 `0x31ea44..0x31ea54`，第三组 `0x31da94..0x31daa4`。第一组在 `isPrivacyMode` 为真时跳过；因此第一组全零不能直接证明 SDK 完全未初始化。
- SDK 时间基准由 `0x2fe1d0` 单例提供，初始化 `0x2fe210` 取 NSDate Unix 秒转 integerValue。调用侧 `0x31e988`、回调侧 `0x3202c8` 减去同一基准，再截断成整数。
- 完成 block `0x31f390` 在 `0x320290` 要求 HTTP status=200，然后按 type 分别写 `+0x48/+0x40/+0x50`；第一组还受 privacy 状态约束。这里只检查 HTTP200，不等于已证明响应业务身份分配成功。
- 最后一项由 `0x37d950`、`0x37df04` 写入，已解析 selector 为 `resumeTime` / `setResumeTime:`；不是传感器坐标。

隔离执行验证了 6 个调用侧分支、12 个响应侧分支（HTTP200/403、privacy 两种状态）、以及原生 formatter 的全部 10 个参数次序。原抓包 `完整版新设备注册登录.chlsj` 也显示第三组在 `/v5/device-info` 调用时从 `[0,0,0]` 变为 `[1,18,0]`，后续签名再变为 `[1,18,21]`；第二次调用则 `[2,26,21]` → `[2,26,28]`。时间线与调用/HTTP200回调写入一致。

因此旧、后期首页 curl 可能来自不同的 SDK 上报进度：有效账号 token 与同一套字段名称，并不保证导出时的 SDK 状态相同。本次早期 b16 中 device-info 次数为 0，后期已出现调用及 HTTP200回调记录。**这些观察不能证明“补发某个激活接口就一定解决”，也不能把后期 b16 常量写到所有账号。** 旧时间为零还可能表示基准后的首秒，不能简单把零解释为失败。

## 现有离线代码的边界

本轮未修改生产签名器、导入器或采集服务。`mtgsig/signer.py:_fresh_a5()` 当前仍按 b2-b17 等于 0/1 来推算 b17；b18 与 b2 同值且非零时跟随。新的原生证据说明这只是历史样本启发式：GET 不应推进 b17，差值超过 1 的 POST 也不应冻结 b17；b18 应依赖独立 SDK userID 状态而非数值相等。b2 的原生计数还具有 32 位回绕边界。

本轮请求全部 POST；#132 的 b18=0、#136 的 b18=77 且不等于 b2，所以这些计数启发式不是本次失败的决定性差异。后续修改应分别持久化 POST 序号及可观测的 SDK userID 状态，兼顾同会话续导入、重载和旧状态迁移；未知状态不能凭 token 猜测。

b16 应从对应设备/会话的真实上报状态或已验证生命周期续接。当前实验只证明同账号观测值替换的影响，尚未证明无需上报交互就能为任意新账号合成服务端接受的生命周期。
